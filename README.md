# AH13 Store

مشروع فعلي لـ Cloudflare Workers: واجهة عربية/إنجليزية، وضع داكن/فاتح، PWA، حساب مستخدم ومطور، مراجعة التطبيقات وتحديث روابطها، مكتبة شخصية، تقييمات وبلاغات وإدارة وسجل إجراءات. لا توجد تطبيقات وهمية أو كلمات مرور افتراضية.

**حالة التسليم:** المشروع أُنشئ من الصفر لأن ملفات النسخة السابقة والشعار الأصلي لم تكن متاحة. لم يتم الوصول إلى حساب Cloudflare أو مخطط قاعدة البيانات الحالية أو تعديل المستودع ah1310/AH13-Store. لا يمكن تأكيد توافق الأعمدة الموجودة بمجرد معرفة أسماء الجداول؛ فحص القاعدة أدناه شرط قبل الإنتاج. الشعار المرفق بديل نصي يمكن استبداله.

## 1. الملفات في مستودع GitHub

فك ZIP ثم انسخ **محتويات** مجلد `AH13-Store` إلى جذر مستودع `ah1310/AH13-Store`، بما فيها `.github` و`.gitignore`. احتفظ بنسخة من النسخة السابقة قبل استبدال ملفاتها. لا ترفع `node_modules` أو `.dev.vars` أو ملفات النسخ الاحتياطية إلى GitHub.

يلزم Node.js 24 وnpm. نفّذ في مجلد المشروع:

```sh
npm ci
npm test
npm run build
npx wrangler login
npx wrangler d1 list
```

افتح `wrangler.json`:

- غيّر `name` إلى **اسم Worker الحالي بالضبط** في Cloudflare حتى يكون النشر تحديثًا له.
- ضع معرّف UUID الخاص بقاعدة **ah13-store-db الموجودة بالفعل** في `database_id` بدل الأصفار. لا تنشئ قاعدة ثانية.
- احتفظ باسم الربط `DB` وبـ `main: src/worker.js` و`assets.binding: ASSETS` و`run_worker_first: true`.
- احتفظ بربط `AUTH_LIMITER`؛ يتوقف تسجيل الحسابات والدخول في الإنتاج إذا غاب، لحماية الحسابات من المحاولات المتكررة.

هذا Worker يحتوي كود `fetch` وأصولًا ثابتة، وليس نشر أصول ثابتة فقط؛ لذلك يمكنه استخدام D1 والأسرار وR2. راجع [إعداد الأصول والربط](https://developers.cloudflare.com/workers/static-assets/binding/).

## 2. حماية البيانات وتهيئة D1

**لا تنفّذ schema.sql مباشرة على القاعدة الحالية، ولا تحذف أي جدول.** نفّذ:

```sh
npm run db:remote
```

الأداة تصدّر نسخة SQL كاملة إلى `backups/` أولًا، ثم تقرأ `PRAGMA table_info` للجداول السبعة وتقارن أسماء الأعمدة وأنواعها والمفاتيح الأساسية. تتوقف دون تعديل عند اختلاف الحقول الأساسية أو وجود حقل إضافي إجباري بلا قيمة افتراضية. عند التوافق، تنشئ الجداول الناقصة فقط والفهارس، وتضيف فقط `users.banned` و`users.session_version` عند غيابهما بقيمة افتراضية صفر. لا تتضمن حذف جداول أو صفوف أو إعادة تسمية أو إعادة كتابة بيانات.

إذا توقفت برسالة **Schema mismatch**، لا تتجاوزها. يُحفظ `schema-inspection.json` وفيه أسماء الأعمدة، دون بيانات المستخدمين. يلزم مواءمة الكود أو إعداد ترحيل إضافي اعتمادًا على هذا الملف وعبارات `CREATE TABLE` الفعلية. فحص الأعمدة لا يضمن توافق CHECK/triggers أو صيغة كلمات المرور القديمة. احتفظ بنسخة التصدير ولا تشاركها علنًا. كلمات مرور النظام الجديد بصيغة `pbkdf2$100000$salt$hash`؛ لا يحوّل كلمات مرور قديمة مجهولة الصيغة تلقائيًا.

العقد المطلوب موثق في `schema.sql`:

| الجدول | الأعمدة الأساسية |
|---|---|
| users | id, email, name, password_hash, role, banned, session_version, created_at |
| apps | id, developer_id, name, url, icon_url, status, created_at |
| app_updates | id, app_id, developer_id, url, status, created_at |
| library | user_id, app_id, created_at |
| ratings | user_id, app_id, score, comment, created_at |
| reports | id, user_id, app_id, reason, status, created_at |
| audit_log | id, actor_id, action, target_id, detail, created_at |

المفاتيح IDs نصية، ومكتبة المستخدم وتقييماته بمفتاح مركب `(user_id, app_id)`. راجع [أوامر D1 والتصدير](https://developers.cloudflare.com/d1/wrangler-commands/).

## 3. إعداد الأسرار وأول أدمن

أنشئ قيمتين مختلفتين عشوائيتين من مدير كلمات المرور، كل منهما **32 حرفًا على الأقل**. لا تستخدم أمثلة ثابتة، ولا تضعهما في `wrangler.json` أو GitHub أو الواجهة.

```sh
npx wrangler secret put SESSION_SECRET
npx wrangler secret put BOOTSTRAP_TOKEN
```

أدخل القيم في المطالبة السرية. `SESSION_SECRET` يوقّع الجلسات، وتغييره يسجل خروج الجميع. `BOOTSTRAP_TOKEN` مخصص لإعداد أول أدمن.

بعد النشر افتح `https://YOUR-WORKER-DOMAIN/#setup`، وأدخل اسمك وبريدك وكلمة مرور جديدة من 12 إلى 128 حرفًا، ثم رمز الإعداد. كلمة المرور تُخزّن مشتقة بـPBKDF2 مع salt عشوائي. عملية إنشاء الأدمن مشروطة ذريًا بعدم وجود حساب بدور admin؛ تسجيل الحساب العادي لا يمنح دور admin مطلقًا. إذا كانت هناك بيانات قديمة تتضمن admin، تتوقف عملية الإعداد بدل إنشاء أدمن آخر.

بعد نجاح الإعداد احذف السر فورًا:

```sh
npx wrangler secret delete BOOTSTRAP_TOKEN
```

رابط `#setup` لا يمنح صلاحية بمفرده. الجلسة في Cookie من نوع HttpOnly وSameSite=Strict وSecure على HTTPS. فحص الدور والحظر يتم على الخادم في كل طلب محمي. تسجيل الخروج وتغيير كلمة المرور والحظر تلغي الجلسات السابقة.

لا يوجد إرسال بريد أو استعادة كلمة مرور ذاتية في هذه النسخة. احتفظ بكلمة مرور الأدمن في مدير كلمات مرور. عند فقدها، يلزم إجراء استعادة بواسطة مالك Cloudflare ذي صلاحية D1؛ لا تفتح باب إعداد الأدمن مجددًا ولا تستخدم كلمة مرور عامة.

## 4. النشر من GitHub المرتبط بـ Cloudflare

في Cloudflare → Workers & Pages → Worker الحالي → Settings → Builds/Git:

1. المستودع `ah1310/AH13-Store` وفرع الإنتاج الفعلي لديك.
2. Root directory هو جذر المستودع إذا نسخت الملفات كما في الخطوة 1.
3. Build command: `npm run build`؛ أداة البناء تثبت الحزم من `package-lock.json`، ويمكن تعيين `npm ci && npm run build` إذا كانت إعدادات البناء لديك لا تثبّتها تلقائيًا.
4. Deploy command: `npx wrangler deploy`.
5. تأكد أن `name` في Wrangler مطابق للـWorker المرتبط، وأن ربط `DB` يشير لقاعدة البيانات الحالية. لا تترك UUID الأصفار.
6. أضف أسرار Worker عبر الأوامر السابقة أو Settings → Variables and Secrets في بيئة الإنتاج. أسرار البناء ليست بديلًا لأسرار تشغيل Worker.
7. ادفع الملفات إلى الفرع المرتبط، ثم افحص سجل البناء.

يمكن اختبار النشر محليًا دون رفعه:

```sh
npx wrangler deploy --dry-run
```

أو النشر يدويًا بعد استكمال الإعداد:

```sh
npm run deploy
```

المجلد `.github/workflows` يتضمن فحصًا تلقائيًا لكل push وPR، ومسار نشر GitHub Actions **يدويًا** (`workflow_dispatch`) لتجنب نشر مزدوج مع ربط Cloudflare الحالي. إذا اخترت Actions بدل ربط Builds، عطّل مسار النشر الآخر وأضف `CLOUDFLARE_API_TOKEN` محدودًا بصلاحية تحرير Worker و`CLOUDFLARE_ACCOUNT_ID` في GitHub Secrets. احتفظ بأسرار التطبيق داخل Worker. الترحيل ليس جزءًا من النشر التلقائي لحماية بيانات الإنتاج.

راجع [إعداد Cloudflare Builds](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/).

## 5. الأيقونات وR2 الاختياري

الافتراضي: المطور يُدخل اسم الموقع ورابط HTTPS ورابط صورة أيقونة HTTPS. لا يحتاج R2. الصور الخارجية تُعرض مباشرة مع `no-referrer`، ويظهر الشعار البديل إن فشلت الصورة. صاحب الصورة الخارجية قد يرى عنوان IP لزائر المتجر.

للرفع المباشر اختياريًا:

```sh
npx wrangler r2 bucket create ah13-store-icons
```

أضف إلى `wrangler.json` خاصية بجانب `d1_databases`:

```json
"r2_buckets": [{"binding":"ICONS","bucket_name":"ah13-store-icons"}]
```

ثم أعد النشر. الرفع يتطلب حساب مطور/أدمن، ويقبل PNG/JPEG/WebP حتى 512 KB مع فحص التوقيع الأولي للملف، ولا يقبل SVG مرفوعًا. تتم خدمة الملفات من `/icons/` دون فتح bucket للعامة. لا يحوّل النظام الصور أو يفحصها بمكافح برمجيات خبيثة. الروابط القديمة داخل الأيقونات لا تُحذف تلقائيًا؛ تابع مساحة R2 من لوحة Cloudflare.

## 6. تجربة محلية

```sh
npm ci
npm run db:local
```

أنشئ `.dev.vars` محليًا فقط بقيم عشوائية مختلفة:

```text
SESSION_SECRET="ضع هنا قيمة عشوائية جديدة لا تقل عن 32 حرفًا"
BOOTSTRAP_TOKEN="ضع هنا قيمة عشوائية أخرى لا تقل عن 32 حرفًا"
```

هذا شكل الملف فقط؛ استبدل النصين. ثم:

```sh
npm run dev
```

افتح عنوان localhost الذي تعرضه الأداة ثم `/#setup`. قاعدة التطوير محلية منفصلة؛ لا تستخدم `--remote` مع dev. PWA يعمل على HTTPS أو localhost، وزر التثبيت يظهر عندما يدعم المتصفح المطالبة؛ في iOS استخدم «إضافة إلى الشاشة الرئيسية».

## الاستخدام والحدود

- المطور يضيف ثلاثة عناصر فقط، والتطبيق يبقى pending حتى موافقة الأدمن. يمكنه طلب رابط جديد، ولا يتغير الرابط المنشور حتى الموافقة.
- «تنزيلاتي» تحفظ المواقع في حساب المستخدم؛ ليست ملفات APK أو متجر تنزيل تطبيقات أصلية. حفظ موقع لا يمنحه عملًا بلا إنترنت.
- كل تطبيق له فتح خارجي بـnoopener/noreferrer. العرض داخل iframe اختياري ومقيّد sandbox؛ لا يتم تجاوز CSP أو X-Frame-Options. لا يمكن كشف منع iframe بدقة لكل موقع، ولذلك يبقى رابط الفتح الخارجي ظاهرًا دائمًا.
- PWA يخزن واجهة المتجر فقط للعمل عند انقطاع الاتصال. طلبات API والبيانات والحسابات لا تُخزّن في service worker؛ يلزم الاتصال لتحميل المكتبة والتطبيقات.
- الأدمن يوافق ويرفض ويحظر التطبيقات، يراجع طلبات التحديث، يحظر ويفك حظر الحسابات، يغيّر user/developer، يغلق البلاغات ويعرض سجل الإجراءات. حسابات الأدمن لا تُعدّل من هذه اللوحة لمنع فقد الوصول.
- لكل مستخدم تقييم واحد قابل للتحديث لكل تطبيق. لا توجد مشتريات أو دفع أو مراجعة تلقائية لسلامة المواقع.
- القوائم تعرض أحدث 500 سجل لكل قسم؛ سجل الإجراءات آخر 200، والتقييمات آخر 100. قبل التوسع أضف pagination حسب حجم الاستخدام.
- استبدل `public/logo.svg` و`icon-192.png` و`icon-512.png` بشعارك الأصلي؛ الأيقونة الكبيرة مربعة مع منطقة آمنة لتثبيت PWA. عند تحديث ملفات الواجهة غيّر اسم CACHE في `public/sw.js` لإزالة النسخة السابقة من ذاكرة التخزين.
- بعد النشر جرّب الحسابات الثلاثة، طلب تطبيق والموافقة عليه وتحديثه والحظر والتقييم من نطاق الإنتاج. الاختبارات المرفقة لا تعني أن بيئة Cloudflare أو بياناتك الحالية اختُبرت عن بعد.

## الاختبارات

`npm test` يستخدم SQLite فعلية داخل Node مع غلاف يحاكي واجهة D1، ويختبر التدفق الكامل وفصل صلاحيات المستخدم/المطور/الأدمن، حماية CSRF، التوقيع والجلسات، الحظر، رفع الصور، حدود المحاولات وحارس المخطط. `npm run build` يفحص صحة الملفات. راجع `TEST-RESULTS.md` لنتائج اختبارات التسليم وحدودها.
